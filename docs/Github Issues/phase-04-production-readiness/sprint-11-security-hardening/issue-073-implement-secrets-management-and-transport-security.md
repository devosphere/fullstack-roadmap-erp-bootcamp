## Summary

Audit the repository for committed secrets, move every remaining secret into environment
configuration, enforce HTTPS and secure cookie attributes, and redact sensitive values from logs.

## Background

Since Issue 006, secrets have lived in environment variables by convention — but a convention is
not a guarantee. Ten sprints of feature branches, quick fixes, and local testing are exactly the
conditions under which a real credential ends up in a commit by accident, and once it is in git
history, deleting the file does not remove it.

This issue treats the repository as guilty until proven innocent: scan the full history, not just
the current tree, and rotate anything found — because a secret that was ever exposed must be
assumed compromised, regardless of whether it is still in the current codebase.

Two things this sprint has already flagged as needing this treatment specifically: **Issue 043's
supplier bank details** and **Issue 070's `JWT_SECRET`** — both are exactly the kind of value that,
if it ever leaked into a log line by accident, would be a serious incident rather than a nuisance.

## User Story

As a Security Administrator,
I want secrets fully removed from source control and history, and transport secured end to end,
So that a leaked repository or intercepted network traffic cannot expose credentials.

- [ ] All remaining secrets sourced from environment configuration, none in source control
- [ ] `.env.example` complete for every module, documented, with no real values
- [ ] HTTPS enforced with redirection from HTTP
- [ ] HSTS header configured (coordinated with Issue 072's security headers)
- [ ] Cookies use `Secure`, `HttpOnly`, and an appropriate `SameSite` attribute
- [ ] Database credentials differ per environment (development, staging, production)
- [ ] Log redaction verified for passwords, tokens, and Issue 043's bank detail fields

- [ ] `JWT_SECRET` and any Issue 070 MFA secrets confirmed environment-sourced and rotated if ever exposed

## Expected Result

No secret value exists in source control, current or historical. Every credential in production is
distinct from development and staging. Traffic is encrypted end to end, and sensitive values never
reach a log file.

## Technical Requirements

**History scan**

```text
Scan every commit, every branch, for patterns matching:
    API keys, JWT secrets, database connection strings with embedded credentials,
    SMTP credentials, bank account patterns

Any match:
    1. Confirm whether it is a real credential or a placeholder
    2. If real, rotate it immediately regardless of git history remediation status
    3. Document the finding and remediation in the security audit log
```

Rewriting git history to remove a committed secret does not undo its exposure — rotation is the
control that matters, not history rewriting, which is noted here to avoid the common mistake of
treating a `git filter-repo` pass as sufficient on its own.

**Environment variable completeness**

For every module (`frontend/`, `backend/`), verify every consumed environment variable is:

```text
1. Listed in that module's .env.example
2. Given a placeholder or empty value, never a real one
3. Validated at application startup, per the pattern from Issue 006/010
```

**HTTPS and transport**

```text
HTTP request  →  301/308 redirect to HTTPS
HTTPS response includes Strict-Transport-Security with a meaningful max-age
```

**Cookie attributes** (if cookies are used for any session-related value)

```text
Secure       — never sent over plain HTTP
HttpOnly     — inaccessible to JavaScript, mitigating XSS token theft
SameSite     — Lax or Strict, chosen and documented
```

**Log redaction verification**

Extend whatever redaction exists from Issue 070's audit logging to explicitly cover:

```text
password, passwordHash
JWT_SECRET, refresh token values
UserMfaSetting.secret
SupplierBankDetail.accountNumber, .accountName, .swiftCode
```

Write a test that deliberately logs a request containing each of these and asserts the log output
does not contain the raw value.

**Rotation procedure**

Document, in `docs/Architecture/`:

```text
- Who can rotate which secret
- The rotation steps per secret type
- How rotation is coordinated with running instances (no downtime requirement, if applicable)
- The schedule for routine rotation, separate from incident-driven rotation
```
